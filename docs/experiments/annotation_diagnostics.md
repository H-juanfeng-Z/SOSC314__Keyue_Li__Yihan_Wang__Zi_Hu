# Annotation measurement diagnostics

This stage follows the earlier encoder comparison and annotation pilots. Its purpose is to establish usable measurements of question intent and first-answer helpfulness before estimating their relationship. It does not establish answer correctness, causal effects, or annotation accuracy.

## Question-intent stability

The fixed development set contains 120 real questions and 28 synthetic diagnostic questions. Seven separate yes/no/uncertain decisions are requested per question (1,036 calls per arm). Qwen2.5-Coder-7B-Instruct and 14B-Instruct are frozen, not fine-tuned. The primary design crosses three representations (processed full text, prose, title), two prompt packages (shared JSON and category-isolated JSON), and greedy decoding versus sampling seeds 314 and 2718: 18 arms. Both prompt packages request one category per call; isolated does not mean a change from multilabel to single-label classification.

The bounded long-run protocol allows additional seeds after the primary design. The completed runs contain 27 arms/27,972 calls for 7B and 18 arms/18,648 calls for 14B. Cross-model interpretation uses matching primary arms, not unequal totals. `run_long.py` and `protocol.py` depend on the existing intent scripts in the same directory.

Full text is previously processed text, not raw HTML. In 100 expanded questions, extracted code was appended without preserving its original position. Prose removes marked code; inline/unmarked code may remain. Inputs contain no answer scores or outcomes. Greedy decoding is deterministic at the algorithm level, not a guarantee of bitwise equality across hardware/software.

Paired analysis excludes questions with any missing, invalid or uncertain category decision, explicitly reporting denominators. Exact set agreement compares all seven labels. Jaccard averages only nonempty unions; two empty sets are counted separately. Bootstrap intervals resample questions 2,000 times with seed 314 and concern mean label-count differences, not accuracy. Shared versus isolated changes a prompt package, so it does not isolate one wording effect.

For full-text greedy prompts, exact agreement is 19.1% (7B, n=115) and 58.8% (14B, n=119). This is evidence of prompt sensitivity, not evidence that either prompt is correct. Disagreement packets generated by `build_disagreement_audit.py` have no reference labels and must not be called manually validated data.

## First-answer helpfulness

Only the original 20 development question/first-answer pairs are used; the reserved 80 remain untouched. The proposed rubric separates relevance, actionability and sufficiency (0/1/2/null), plus an overall ordinal judgment. It is a project rubric, not an externally validated scale. Evidence IDs must refer to supplied answer lines, but passing this check does not establish evidential support. The validator does not enforce the prompt's 50-word reason limit or prevent citations of code-marker-only lines.

- Boundary diagnostics: original, mismatched, empty and encouragement answers, each under boundary and boundary-plus-JSON-example prompts. The shared runner also implements additional nonanswer controls. JSON examples illustrate format; they are not training data.
- Content sensitivity (14B): 20 pairs x four variants x two prompts = 160 calls, 159 schema-valid. Variants retain the original, remove marked code, retain only marked code, or retain the first half of characters. Empty and unchanged variants must not be interpreted as ordinary content-removal pairs. The half-prefix can cut a sentence or code block.
- Code grounding (14B): 13 code-containing pairs x four variants x two prompts = 104 calls, 103 schema-valid. A different development answer donates nonidentical marked code selected by nearest character length, then pair ID. Prose remains unchanged; code is consolidated into the first block, which is a structural confound. Foreign code is not guaranteed irrelevant.
- Prompt factorial (14B): the same 13 pairs x four answer conditions x four prompt arms = 208 calls, all schema-valid. Arms are baseline, added evidence instructions, added dimension definitions, and both. Baseline is the boundary-plus-JSON prompt. Exact instructions are constants in `run_rubric_factorial.py`.

The factorial rated 3/13 swapped-code answers substantial under baseline, 1/13 with evidence instructions, 4/13 with dimension instructions, and 2/13 with both. Lower is not automatically better: useful original prose may remain. Actionability and sufficiency differed in 0/52, 0/52, 4/52 and 3/52 judgments respectively. More differentiated scores do not establish validity. These are adaptively developed diagnostics on reused cases, not an independent test.

## Relation to the overall research question

Intent and helpfulness annotations can ultimately support an analysis of whether kinds of help-seeking are associated with receiving useful assistance. The present join has at most 20 pairs and a strong ceiling: 14B labels all original answers substantial under the boundary prompt, and 18/20 under boundary-plus-JSON. We therefore did not fit a downstream association regression. All-answer comparisons and asker follow-up remain future work, not completed results here.

## Reproduction and artifacts

Programs remain in functional directories, not weekly program folders. From the repository root:

```bash
python scripts/helpfulness/test_diagnostic_transforms.py
python scripts/helpfulness/summarize_diagnostics.py
python scripts/intent_annotation/analyze_measurement_bridge.py --root tables/annotation_diagnostics/decisions --out LOCAL_NEW_OUTPUT
python -m pip install Pillow==12.3.0
python scripts/visualization/make_annotation_diagnostics.py
```

The paired analyzer refuses to overwrite its results file; choose a fresh output directory. Plotting reads the versioned `tables/annotation_diagnostics/intent_stability/results.json` and helpfulness summary. Recomputed timestamps and export-file hashes can differ from the original server summaries; scientific statistics should match. Pillow generates PNGs and the same plotting code writes SVGs; these are data visualizations, not generated artwork.

The `decisions/` directory includes non-text per-call exports: status, identifiers, category decisions/ratings and selected diagnostic fields. It omits question/answer text, prompts, raw completions, reasons and evidence quotations. It is sufficient to recompute the published paired statistics and cell counts, but not to independently reassess semantic judgments. Original logs and inputs are retained privately; export source hashes provide provenance, not access. The disagreement extraction and content-paired audit require their original input/manifest files, which are not bundled here.

To rerun GPU inference, supply local model weights and the original input files:

```bash
python scripts/helpfulness/run_helpfulness_grounding.py --data PATH_TO_BLINDED_PAIRS --model PATH_TO_MODEL --out NEW_RUN
python scripts/helpfulness/run_content_sensitivity.py --data PATH_TO_BLINDED_PAIRS --model PATH_TO_MODEL --out NEW_RUN
python scripts/helpfulness/run_code_grounding.py --data PATH_TO_BLINDED_PAIRS --model PATH_TO_MODEL --out NEW_RUN
python scripts/helpfulness/run_rubric_factorial.py --data PATH_TO_BLINDED_PAIRS --model PATH_TO_MODEL --out NEW_RUN
python scripts/intent_annotation/run_long.py --data PATH_TO_CASES --model PATH_TO_MODEL --out NEW_RUN --target-hours 8
```

Recorded inference environment: Python 3.12, torch 2.5.1+cu124, transformers 4.57.6, float16, local safetensors, no remote model code. Allocate a CUDA GPU before running; these scripts do not schedule resources. Helpfulness uses greedy generation, input limit 7,500 tokens (skip rather than truncate), output limit 256, seed 314. Intent outputs are limited to 160 tokens; sampling uses temperature 0.3/top-p 0.9. The long-run runner conservatively requires 36 GiB free GPU memory. Model revisions: 7B `c03e6d358207e414f1eca0bb1891e29f1db0e242`; 14B `aedcc2d42b622764e023cf882b6652e646b95671`.

The 100-pair source hash is `40ab362611f9284840b83635ddc23d8e0b45714ef034753c6249963ca647515b`; the intent-case source hash is `2e9553e414e623f602f983359a95dbea450c96a8f8b5d1c56a4aaccc0c2c2936`.
